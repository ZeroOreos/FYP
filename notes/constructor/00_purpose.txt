# Constructor Purpose

Goal
- FYP goal: evaluate layered defenses against realistic manipulated-face attacks, with emphasis on locally deployable models and practical protection choices across the attack lifecycle
- Paper-direction goal: position the project as an information-forensics and security study rather than as a pure attack-benchmark paper
- This defensive evaluation goal was part of the intended FYP plan from the start; the repo has simply reached the attack-benchmark stage first
- Current implemented phase: build and validate the manipulated-probe generation and verification-evaluation pipeline
- Current main question: can manipulated probes be accepted as the victim identity by face verification systems
- Intended paper question: how well can proactive protection, recognizer-side hardening, and post-hoc detection methods reduce or expose those manipulations while remaining practical to shrink, port, and run locally
- Priority attack families for the current phase: face swap and reenactment
- Secondary current-phase tasks: recognition robustness, privacy protection, readable benchmarking

Project framing
- Treat the repo as a staged project rather than a finished defense benchmark
- Phase 1: build attack backends, pair generation, materialization, and verification evaluation
- Phase 2: add defense methods and evaluate them by defense layer against the generated manipulations, including local deployment constraints
- WIFS framing rule: the attack pipeline is benchmark-construction infrastructure for a forensics / security contribution, not the paper endpoint by itself
- WIFS contribution target:
- show how manipulated probes affect face verification under realistic attack diversity
- show how defense layers differ in what they prevent, what they detect, and what they cost to deploy locally
- turn local deployability into an explicit evaluation axis rather than a side implementation note
- Protection / prevention model space is part of the intended project structure, even where implementation is still incomplete
- Recognition diversity matters because the current attack phase still depends on face-verification systems as the measurement instrument; avoid over-claiming from a single verifier
- Current recognition anchor set is `InsightFace`, `FaceNet`, `AdaFace`, and `MagFace`
- Defense-model positioning rule:
- proactive privacy / cloaking methods act before misuse by perturbing source images
- recognizer-side hardening methods try to make verification itself less vulnerable
- post-hoc detection methods inspect probes or outputs for evidence of manipulation
- Initial defense-model candidate set by layer:
- proactive privacy / cloaking shortlist:
- `Fawkes`: primary proactive cloaking baseline
- `FaceShield`: proactive facial-image protection baseline
- `FALCO`: proactive anonymization baseline with clean open-code / open-license positioning
- `DeepPrivacy2`: maintained proactive anonymization target and practical successor to legacy `DeepPrivacy`
- legacy `DeepPrivacy`: historical baseline only; use it only if the old checkpoints become reachable again
- optional later proactive candidate: `Facial Attributes Obfuscation`
- post-hoc detection shortlist:
- `UniDefense`: practical first detector baseline
- `M2F2-Det` stage-1: lighter detector candidate
- `M2F2-Det` full Hugging Face model: heavier interpretable detector candidate
- Attack diversity matters because it creates a more realistic test bed for the later defensive phase, not because every backend is equally central to the thesis
- Paper-scope warning:
- do not let backend count become the main claim
- do not flatten proactive protection, recognizer hardening, and post-hoc detection into one generic leaderboard
- prefer one sharp forensics / security story over a maximal system inventory

Notes contract
- Constructor docs live under `notes/constructor/`
- Working logs live under `notes/working/`
- References stay in `notes/references.txt`
- Every attack backend must keep an exact adaptation log in `notes/working/20_backend_adaptations.txt`
- End-state cleanup rule: once backend documentation is properly centralized in constructor, working, and references, per-model status clutter in READMEs should be deleted or cleaned up rather than left duplicated
