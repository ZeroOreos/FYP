Paper-alignment and runtime decision notes
- The paper claim should be framed as a defended target recognizer trained under a multi-recognizer objective ensemble and a multi-attacker adversarial ensemble.
- This is stronger and more accurate than saying the current main path is a deployment-time ensemble of independent recognizer backbones.
- The current recognizer ensemble is `ArcFace`, `CosFace`, and `CurricularFace` margin-head pressure over the target embedding.
- For the strongest literal multi-recognizer wording, add held-out external recognizer-backbone evaluation or a frozen external recognizer teacher path before final submission.
- The current attacker ensemble is aligned with robust-optimization and ensemble-adversarial-training precedent: use strong iterative white-box pressure, transfer/black-box pressure, and diverse evaluation attacks.
- The evaluation story must stay non-overlapping with training pressure:
- report trained attacks separately from held-out or stronger attacks
- report per-attack metrics and aggregate robustness
- report per-recognizer metrics, recognizer-ensemble gain vs best single, and calibration
- report verification metrics: EER, ROC-AUC, TAR@FAR, best threshold, and mean positive/negative cosine
- report efficiency metrics: global image/s, attack-generation share, step share, GPU peak memory, and attacker policy fractions
- use `scripts/evaluate_paper_breakdown.py` after checkpoints are available to produce the paper-facing clean/trained-attack/stress-attack breakdown across the target and recognizer heads
- write that breakdown as `paper_breakdown.json`, `paper_breakdown.csv`, and `paper_breakdown.md` inside the run directory for export
- The old wrong `full-ensemble` history is still useful for runtime diagnosis:
- clean warmup at batch `128` was loader-light and GPU-heavy enough
- recognizer pressure is now stage-gated with `recognizer_start_epoch` so clean warmup can remain target-only and fast before the multi-recognizer objective turns on
- target Partial FC remains at `0.3`, while auxiliary recognizer heads use `recognizer_partial_fc_negative_sample_rate = 0.12` to avoid OOM from four simultaneous many-class margin heads
- shallow adversarial batch `48` was stable around `380ms` attack generation and roughly `600` global img/s on non-heavy-eval epochs
- full adversarial batch `32` was faster and safer than `40` in the old evidence
- full adversarial batch `40` increased attack-generation time and memory pressure enough to reduce throughput and trigger OOM risk
- The source paper configs therefore pin full adversarial batch size to `32` for paper safety unless a new probe proves a higher value improves throughput without OOM.
- Do not weaken the full attack objective just to go faster; any FGSM/free-style shortcut should be an explicit speed ablation, not the main result.

- Standard ingredients we are reusing rather than claiming as new: margin-loss face-recognition families (`ArcFace`, `CosFace`, `CurricularFace`), `SGD`, `Partial FC`, optional sub-center `ArcFace`, distributed PyTorch / `DDP`, `SyncBatchNorm`, gradient accumulation, mixed precision, clean evaluation, white-box adversarial training, and the current native primary attackers `PGD`, `BPFA`, and `DFANet`.
- Standard data-engineering direction: manifest-backed training on aligned `WebFace4M`, optional server-side JPEG extraction behind the same manifest contract, and ordinary checkpoint / history / metrics artifact writing.
- Specialized repo behavior: the repo now supports both a legacy composite-target `joint_pool` path and a newer explicit target-plus-recognizer-ensemble path.
- Specialized repo behavior: `joint_pool` means one composite defended target with internal `ArcFace + CosFace + CurricularFace` heads, not the same thing as an external recognizer ensemble.
- Specialized repo behavior: the training contract uses an explicit `three_stage` depth schedule with clean warmup, shallow adversarial depth, and full adversarial depth instead of one fixed attack depth from epoch `1`.
- Specialized repo behavior: primary attacker families are rotated by batch through an attack-policy sampler instead of blended uniformly into every batch.
- Specialized repo behavior: ensemble-aware hard-pair mining is part of the defended update rule and is staged over training rather than kept fixed from the start.
- Specialized repo behavior: the repo keeps a strict split between native in-loop primary attackers and cached external surrogate pressure.
- Specialized repo behavior: shard-aware distributed sampling is implemented to preserve throughput on manifest-backed `WebFace4M` data.
- Specialized repo behavior: run reporting is tuned for this repo, including structured epoch records in `metrics.jsonl`, explicit validation-loss fields in epoch summaries, and DDP-aware global progress display instead of rank-local progress percentages.

What research says to do next
- frame the system as adversarial recognizer training with one defended target model, an external recognizer ensemble, and an explicit attacker ensemble
- keep the defended recognizer set compact and paper-legible instead of expanding into too many side families
- use the foundational margin-loss recognizers that make the comparison logic easy to justify in the paper
- keep `joint_pool` available as a legacy or ablation composite-target path, not as the only interpretation of recognizer ensembling
- train the main paper path as one target under recognizer-ensemble pressure and attacker-ensemble pressure
- keep the attack side ensemble-aware with explicit primary attackers and explicit surrogate attackers
- keep the main recognizer ensemble as `ArcFace`, `CosFace`, and `CurricularFace`
- define the primary attacker set as `PGD`, `BPFA`, and `DFANet`
- define the surrogate attacker set as `AdvFaceGAN`, `Adv-Makeup`, and `Greedy-DiM`
- move the local serious training set to aligned `WebFace4M`
- keep `WF42M` as the ceiling target for larger compute only
- evaluate clean performance, white-box robustness, black-box transfer, cross-recognizer transfer, and OOD corruptions or appearance variations
- keep FR plus FAS or PAD as a realism extension, not the initial core claim
- keep the defended recognizer update rule Madry-style and keep the external diversity pressure Tramer-style
- use a `3`-stage training-depth curriculum instead of forcing full attack strength from epoch `1`
- stage `1`: clean warmup to stabilize backbone and feature geometry
- stage `2`: shallow adversarial depth with weak fast attacks, reduced budgets, and partial attacker rotation
- stage `3`: full adversarial depth with full joint recognizer-pool pressure and full primary-attacker rotation
- keep full multi-attack evaluation periodic, not every epoch
- rotate one primary attacker family per batch instead of blending every family into every batch
- use a default `50%` clean / `50%` adversarial batch split
- use a default adversarial intent split of `50%` impersonation / `50%` dodging
- keep morphing, makeup, and generative attacks as periodic-training or eval-time pressure, not the default every-batch path
- phrase the main claim as a moderately strong multi-recognizer, multi-attack ensemble claim, not as a claim that this repo has discovered the final FR robustness standard
- expect the largest gains from the broader ensemble conditions to appear in robust loss, robust accuracy, attack success rate, and transfer behavior, while clean-only baselines may still look best on clean accuracy

Completed paper ladder readout
- The completed local paper ladder now has five primary rows: `baseline-clean`, `recognizer-ensemble-only`, `single-attack-only`, `attack-ensemble-only`, and `full-ensemble`.
- Final clean validation: `baseline-clean` `99.23%`, `recognizer-ensemble-only` `99.23%`, `attack-ensemble-only` `93.98%`, `full-ensemble` `93.40%`, and `single-attack-only` `79.69%`.
- Final robust validation is available for the attacked rows: `single-attack-only` `30.00%` under its trained `PGD` eval, `attack-ensemble-only` `52.32%` averaged over `PGD/BPFA/DFANet`, and `full-ensemble` `56.55%` averaged over `PGD/BPFA/DFANet`.
- Comparability caveat: rerun `single-attack-only` posthoc robust with the shared `PGD/BPFA/DFANet` eval suite before using it in an averaged robustness table.
- Final attack success rate is lower for `full-ensemble` than `attack-ensemble-only`: `39.45%` versus `44.32%`.
- Final per-attack robust accuracy favors `full-ensemble` over `attack-ensemble-only` on every in-loop family: `PGD` `52.55%` versus `45.45%`, `BPFA` `69.56%` versus `66.09%`, and `DFANet` `47.55%` versus `45.43%`.
- `single-attack-only` is a useful narrow-training contrast: despite training on `PGD`, its final `PGD` robust accuracy is only `30.00%`, far below the broader attack-ensemble and full-ensemble rows.
- Final posthoc verification is strongest for clean/recognizer-only rows: `baseline-clean` pair accuracy `99.96%`, `EER=0.047%`; `recognizer-ensemble-only` pair accuracy `99.96%`, `EER=0.041%`.
- Final posthoc verification for `attack-ensemble-only` remains strong: pair accuracy `98.33%`, `EER=1.78%`, `ROC-AUC=99.75%`.
- Final posthoc verification for `single-attack-only` is poor relative to the other rows: pair accuracy `89.74%`, `EER=12.82%`, `ROC-AUC=92.01%`.
- Final `full-ensemble` posthoc verification is now pulled locally: pair accuracy `98.21%`, `EER=1.93%`, `ROC-AUC=99.73%`.
- Local artifact caveat: the currently pulled `baseline-clean/posthoc-robust.json` and `recognizer-ensemble-only/posthoc-robust.json` are skipped artifacts with `reason=no_attackers`; rerun those posthoc robust probes after syncing the `eval_attackers` patch before comparing clean-only or recognizer-only robustness against attacked rows.
- Local artifact caveat: `single-attack-only` also needs a shared-suite posthoc robust probe because the fair paper comparison should evaluate every row against the same `PGD/BPFA/DFANet` suite.
- Crosscheck caveat: older `summary.json.best.val_verification_eer` and `summary.json.best.val_robust_attack_success_rate` fields were produced by a generic max-is-best helper, so paper tables should use final/latest/posthoc EER and attack-success values instead of those legacy `best` fields.
- Paper interpretation: the clean and recognizer-only rows show the high clean/verification ceiling; broader adversarial training lowers clean/verification performance but greatly improves robust validation; adding recognizer-ensemble pressure on top of attack-ensemble training gives the best final robust result among completed robust rows.
- Paper caution: do not claim that multi-recognizer pressure improves clean accuracy or verification accuracy; the current evidence says its main benefit is adversarial robustness and lower attack success relative to attacker-only training.
- Paper caution: for already completed clean-only and recognizer-only artifacts, do not compare them against attacked rows on robust metrics until non-skipped `posthoc-robust.json` files have been generated and pulled; future runs now backfill this final robustness row automatically.

Next-step paper positioning: modern attacker stress testing
- The current paper should not claim broad robustness against all modern face-recognition attacks.
- The completed core should be framed as supervised multi-recognizer, multi-attacker adversarial training evaluated against its explicit in-loop attack families and ablation ladder.
- A strong and honest next step is a posthoc stress-test suite against more modern or more semantically realistic attackers.
- This next step should be described as future validation or follow-up work, not as evidence already established by the current completed ladder.
- The most defensible next-step lineup is:
- stronger online white-box attacks such as higher-budget `PGD`, margin/CW-style attacks, and parameter-free robustness checks such as AutoAttack/APGD
- stronger transfer-oriented face attacks such as TransMix-style transfer attacks
- semantic or generative face attacks such as adversarial makeup and diffusion-based face privacy attacks
- morphing attacks such as Greedy-DiM evaluated with a verification/morph protocol rather than only closed-set classification
- physical or cross-system realism extensions such as patch/makeup attacks and FR-plus-FAS/PAD stacks
- The paper can say these stress tests are the natural next step because the current innovation is in the training framework and ablation evidence, while modern generative and physical attackers require separate faithful attack implementations or cached generated adversarial images.
- Do not fake modern attack coverage by renaming existing `PGD`, `BPFA`, or `DFANet` runs; only count a modern attack if its actual method or generated adversarial images are used.

Latest server-run implementation and obstacles

- `Training/config.py`, `Training/engine.py`, and `scripts/render_cloud_config.py` now support `gradient_accumulation_steps` so the serious CUDA path can keep a larger effective batch while reducing per-step memory pressure
- the training loop now delays optimizer steps across microbatches and uses `DistributedDataParallel.no_sync()` on non-step microbatches to avoid unnecessary gradient synchronization during accumulation
- the server workflow was validated far enough to confirm that `torch`, `torchrun`, the full `WebFace4M` shard set, and manifest-backed loading are all functioning in the remote environment
- the remote `WebFace4M` data path currently exists under `/home/wen/data/FYP/Dataset/WebFace4M`, with shard files confirmed present on the server and manifest regeneration working when the correct target root is used
- the original cloud bootstrap script assumption was too optimistic for this machine: `/shared/...` was not writable, and the server also had no outbound network path to download `WebFace4M` directly
- the practical workaround was to treat the server dataset as an uploaded local asset rather than a remotely bootstrapped internet download
- a local extraction attempt for `WebFace4M` JPEGs was started and then intentionally canceled; cleanup removed the partial `images/` tree and restored the local dataset folder to the shard-backed state
- the serious `iResNet100` CUDA config currently starts cleanly under `torchrun`, but the original `batch_size=32` per GPU run hits CUDA OOM on `24GB` `RTX 4090 D` cards even before meaningful progress through epoch `1`
- reducing to `batch_size=1` is not a valid fallback for this model as currently written because the backbone hits a training-time batch-normalization failure on tensors of shape `torch.Size([1, 512])`
- the next serious server-side tuning path is therefore not just "smaller batch"; it is "real distributed training plus `SyncBatchNorm` plus accumulation", with `batch_size >= 2` per rank and the config explicitly setting `use_distributed=true` and `use_sync_batchnorm=true`
- a key operational gotcha during debugging was that launching with `torchrun` alone is not enough for this repo; if the rendered JSON still says `use_distributed=false`, the run will report `world_size=8` but not actually take the intended internal DDP path
- the current open risk is that `iResNet100` full-set training may still need additional memory or normalization tuning even after accumulation and true DDP are enabled, so the serious paper run is closer than before but not yet proven stable end to end
