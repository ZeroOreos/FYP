Current repo state

- The repo is intended to be the full and final model-training repo.
- The active entrypoint is `main_train_ensemble.py`.
- Files under `notes/reports/` are non-repo-impacting report artifacts and writeups.
- Reports must be treated as downstream descriptions of the repo state, not as the source of truth for repo decisions.
- If a report conflicts with code, configs, run artifacts, or core notes, trust the repo implementation and repair the report instead of steering the repo toward the report.
- The current trainable target is `ArcFace` on `ResNet18` as the current real verification-stage backbone.
- The intended defended recognizer ensemble for the paper is `ArcFace`, `CosFace`, and `CurricularFace`.
- The intended attacker ensemble for the paper is split into primary attackers and surrogate attackers.

- `WebFace4M` is now the only active training and verification data path in the repo.

What is standard versus what is specialized here
- Standard ingredients we are reusing rather than claiming as new: margin-loss face-recognition families (`ArcFace`, `CosFace`, `CurricularFace`), `SGD`, `Partial FC`, optional sub-center `ArcFace`, distributed PyTorch / `DDP`, `SyncBatchNorm`, gradient accumulation, mixed precision, clean evaluation, white-box adversarial training, and the current native primary attackers `PGD`, `BPFA`, and `DFANet`.
- Standard data-engineering direction: manifest-backed training on aligned `WebFace4M`, optional server-side JPEG extraction behind the same manifest contract, and ordinary checkpoint / history / metrics artifact writing.
- Specialized repo behavior: the defended recognizer target can be a jointly trained `joint_pool` over `ArcFace + CosFace + CurricularFace` instead of only a single recognizer.
- Specialized repo behavior: the training contract uses an explicit `three_stage` depth schedule with clean warmup, shallow adversarial depth, and full adversarial depth instead of one fixed attack depth from epoch `1`.
- Specialized repo behavior: primary attacker families are rotated by batch through an attack-policy sampler instead of blended uniformly into every batch.
- Specialized repo behavior: ensemble-aware hard-pair mining is part of the defended update rule and is staged over training rather than kept fixed from the start.
- Specialized repo behavior: the repo keeps a strict split between native in-loop primary attackers and cached external surrogate pressure.
- Specialized repo behavior: shard-aware distributed sampling is implemented to preserve throughput on manifest-backed `WebFace4M` data.
- Specialized repo behavior: run reporting is tuned for this repo, including structured epoch records in `metrics.jsonl`, explicit validation-loss fields in epoch summaries, and DDP-aware global progress display instead of rank-local progress percentages.

What research says to do next
- frame the system as adversarial recognizer training with a defended recognizer pool and an attack pool
- keep the defended recognizer set compact and paper-legible instead of expanding into too many side families
- use the foundational margin-loss recognizers that make the comparison logic easy to justify in the paper
- train the defended recognizer pool jointly and keep the attacker side diverse and explicit
- keep the attack side ensemble-aware with explicit primary attackers and explicit surrogate attackers
- keep the main recognizer ensemble as `ArcFace`, `CosFace`, and `CurricularFace`
- define the primary attacker set as `PGD`, `BPFA`, and `DFANet`
- define the surrogate attacker set as `AdvFaceGAN`, `Adv-Makeup`, and `Greedy-DiM`
- move the local serious training set to aligned `WebFace4M`
- keep `WF42M` as the ceiling target for larger compute only
- evaluate clean performance, white-box robustness, black-box transfer, cross-recognizer transfer, and OOD corruptions or appearance variations
- keep FR plus FAS or PAD as a realism extension, not the initial core claim
- keep the defended recognizer update rule Madry-style and keep the external diversity pressure Tramer-style
- use a `3`-stage training-depth curriculum instead of forcing full attack strength from epoch `1`
- stage `1`: clean warmup to stabilize backbone and feature geometry
- stage `2`: shallow adversarial depth with weak fast attacks, reduced budgets, and partial attacker rotation
- stage `3`: full adversarial depth with full joint recognizer-pool pressure and full primary-attacker rotation
- keep full multi-attack evaluation periodic, not every epoch
- rotate one primary attacker family per batch instead of blending every family into every batch
- use a default `50%` clean / `50%` adversarial batch split
- use a default adversarial intent split of `50%` impersonation / `50%` dodging
- keep morphing, makeup, and generative attacks as periodic-training or eval-time pressure, not the default every-batch path

Best local training set under about `20GB`
- Best recommendation: use aligned `WebFace4M`, not an ad hoc `WF42M` slice.
- Reason: it is a real face-recognition training set with published use in modern recognition work, and the gzip WebDataset release appears small enough to fit the budget.
- Avoid a random `WF42M` cut unless it is curated by identity balance, image count per identity, and alignment quality.

Current tuned recipe under that budget
- recognizer ensemble: `ArcFace`, `CosFace`, and `CurricularFace`
- primary attacker set: `PGD`, `BPFA`, `DFANet`
- surrogate attacker set: `AdvFaceGAN`, `Adv-Makeup`, `Greedy-DiM`
- final serious `ArcFace` target: `iResNet100`
- current verification-stage backbone path: `ResNet18`
- optimizer: `SGD`
- train the defended recognizer pool jointly under rotating attacker pressure
- treat a `WebFace4M` slice as medium-scale adversarial fine-tuning, not full from-scratch large-scale pretraining
- first serious schedule: `24` epochs
- use `2` epoch LR warmup
- use `2-3` clean warmup epochs before adversarial pressure
- use stage `2` shallow adversarial depth before full budgets
- keep `50%` clean and `50%` adversarial samples in the final full-depth stage
- rotate by batch through white-box, transfer, and FR feature-level primary attacker families
- keep adversarial targets split `50%` impersonation and `50%` dodging
- keep hard-pair mining modest early and ramp it later
- use `Partial FC` for the serious many-class recipe
- use sub-center `ArcFace` for the serious `ArcFace` preset
- keep dropout at `0.0` in the tuned serious presets instead of `0.4`
- keep morphing, makeup, and generative attacks periodic or eval-time rather than the default main-loop attacker path
- keep the final research framing centered on the named primary-attacker and surrogate-attacker sets, while the code treats standard primary attackers as the main loop and surrogate attackers as cached external pressure
- keep manifests as the training contract for `WebFace4M`; optionally extract JPEGs on the server if direct file reads benchmark better there
- target effective batch around `512` when hardware allows; otherwise use accumulation later instead of weakening the core method
- decay the LR around `40-45%`, `75%`, and `90%` of the first serious schedule
- keep checkpointing and loader-worker counts tuned for the actual final device, not left always-on by default

Latest server-run implementation and obstacles
- the first serious remote `WebFace4M` `ArcFace` `iResNet100` path is now wired through `uv`, `torchrun`, and rendered server-local configs instead of the older local-only assumption
- `Training/config.py`, `Training/engine.py`, and `scripts/render_cloud_config.py` now support `gradient_accumulation_steps` so the serious CUDA path can keep a larger effective batch while reducing per-step memory pressure
- the training loop now delays optimizer steps across microbatches and uses `DistributedDataParallel.no_sync()` on non-step microbatches to avoid unnecessary gradient synchronization during accumulation
- the server workflow was validated far enough to confirm that `torch`, `torchrun`, the full `WebFace4M` shard set, and manifest-backed loading are all functioning in the remote environment
- the remote `WebFace4M` data path currently exists under `/home/wen/data/FYP/Dataset/WebFace4M`, with shard files confirmed present on the server and manifest regeneration working when the correct target root is used
- the original cloud bootstrap script assumption was too optimistic for this machine: `/shared/...` was not writable, and the server also had no outbound network path to download `WebFace4M` directly
- the practical workaround was to treat the server dataset as an uploaded local asset rather than a remotely bootstrapped internet download
- a local extraction attempt for `WebFace4M` JPEGs was started and then intentionally canceled; cleanup removed the partial `images/` tree and restored the local dataset folder to the shard-backed state
- the serious `iResNet100` CUDA config currently starts cleanly under `torchrun`, but the original `batch_size=32` per GPU run hits CUDA OOM on `24GB` `RTX 4090 D` cards even before meaningful progress through epoch `1`
- reducing to `batch_size=1` is not a valid fallback for this model as currently written because the backbone hits a training-time batch-normalization failure on tensors of shape `torch.Size([1, 512])`
- the next serious server-side tuning path is therefore not just "smaller batch"; it is "real distributed training plus `SyncBatchNorm` plus accumulation", with `batch_size >= 2` per rank and the config explicitly setting `use_distributed=true` and `use_sync_batchnorm=true`
- a key operational gotcha during debugging was that launching with `torchrun` alone is not enough for this repo; if the rendered JSON still says `use_distributed=false`, the run will report `world_size=8` but not actually take the intended internal DDP path
- the current open risk is that `iResNet100` full-set training may still need additional memory or normalization tuning even after accumulation and true DDP are enabled, so the serious paper run is closer than before but not yet proven stable end to end

Recent implementation notes
- terminal logging was intentionally trimmed so batch-window reports still go to `train.log` on the configured interval, but they are no longer all echoed to the interactive terminal
- epoch summaries now print validation-loss fields alongside the existing accuracy fields because validation loss is currently a more informative signal than the composite training loss alone
- the training progress display was corrected to use global DDP sample counts rather than rank-`0` local counts, so low percentage-used readouts in distributed runs should now be treated as a resolved display bug rather than a data-coverage problem
