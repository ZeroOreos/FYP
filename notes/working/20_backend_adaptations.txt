# Backend Adaptations

Purpose
- Keep an exact per-backend record of what was changed locally to make an upstream method run in this repo
- Use this for methods writing, reproducibility notes, and honesty about fidelity

Format
- Model: name
- Status: verified / blocked / scaffolded / partial
- Upstream repo
- Upstream snapshot
- Local wrapper
- Canonical runtime env
- Accelerator status
- Assets used
- Verification date
- Verification input
- Verification output
- Working command
- Local files patched
- Local adaptations
- Fidelity note
- Remaining caveats

Runtime policy
- Move toward one canonical runtime env per model under `Backends/workdirs/<model>/`
- Keep envs isolated by model rather than forcing a single repo-wide PyTorch stack
- Record accelerator support per model in these notes after the env is proven locally
- Add a second model-local env only when a distinct accelerator-oriented stack is genuinely needed
- Near-term runtime goal: try to build a practical MPS-capable venv path that all active models can use, while falling back to model-local envs where compatibility still diverges
