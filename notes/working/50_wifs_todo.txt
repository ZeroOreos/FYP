# WIFS TODO

Purpose
- Keep implementation and writing decisions pointed toward a WIFS-style information forensics and security paper
- Treat attack benchmarking as supporting infrastructure for the defense-layer and forensic-analysis story

Immediate paper-direction tasks
- lock one paper question and keep it visible in later notes:
- how effective are layered locally deployable defenses against realistic manipulated-face attacks on face verification
- define the minimum publishable evaluated set rather than growing the method zoo:
- attacks: keep the verified working set centered on `simswap`, `reface`, `fomm`, `advfacegan`, and `mordiff`
- recognizers: keep `InsightFace`, `FaceNet`, `AdaFace`, and `MagFace`
- defenses: prioritize one proactive path plus one post-hoc detector path before broadening
- choose the first paper-stable defense core:
- proactive: `Fawkes` or `FALCO`
- post-hoc: `UniDefense` or `M2F2-Det` stage-1
- keep recognizer-side hardening as a later extension unless a strong locally runnable candidate becomes available quickly

Evaluation tasks
- define one shared manipulated-probe benchmark subset that all evaluated defenses reuse
- add deployment-oriented metrics beside security metrics:
- runtime
- device support
- environment complexity
- fidelity label: benchmark-faithful, approximation-grade, or runtime-validity-only
- report verifier-specific results first, then cross-recognizer trends
- keep proactive protection results separate from post-hoc detector leaderboards
- add forensic interpretation targets:
- which attack families transfer across recognizers
- which defenses fail closed versus fail silently
- which methods remain useful after local shrinking / porting constraints

Writing tasks
- draft the paper narrative as:
- threat: manipulated probes can be accepted by verifiers
- benchmark: realistic local attack set and multi-recognizer verification
- defense study: layered defenses evaluated on the same manipulated probes
- forensic/security takeaway: local practicality changes which defenses are truly usable
- keep implementation honesty explicit:
- mark smoke-test-only paths clearly
- mark approximation-grade reproductions clearly
- do not over-claim blocked CUDA-only or random-init detector paths
- plan figures / tables around WIFS fit:
- attack success table by recognizer and attack family
- defense table by layer with security and deployment metrics
- compact qualitative discussion of where detection versus prevention helps most

Decision rules
- do not spend major effort adding more attacks unless they change the paper conclusion
- do not spend major effort adding more recognizers unless one current recognizer must be replaced
- prefer depth on a smaller defense set over breadth on a large unfinished set
- any result used in the paper must carry an explicit fidelity label and reproduction note
