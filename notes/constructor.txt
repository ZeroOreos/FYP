# FYP Constructor

## Goal
- Priority task: face-swap and reenactment attacks against face verification
- Main question: can manipulated probes be accepted as the victim identity
- Secondary tasks: recognition robustness, privacy protection, readable benchmarking

## Writing Style Contract
- Target: README text, code comments, short docs, usage notes, warning text, CLI help text when practical
- Tone: human, sharp, plain, low-clutter
- Priority: clarity first, brevity second, completeness third
- Avoid: soft framing, filler, corporate phrasing, tutorial voice, paragraph sprawl

## Writing Style Rules
- Prefer lists for how-to content
- Prefer short blocks over dense paragraphs
- Use full sentences only when needed for ambiguity control
- Short sentence style is preferred
- Sentence fragments are allowed when clearer
- Warnings should be blunt and cut off fast
- Example warning style:
- `Warning: wrong CUDA version. Broken env.`
- `Warning: forced backend missing. Hard fail.`
- Do not pad warnings with reassurance unless the action is genuinely unclear
- Do not narrate obvious transitions
- Do not add background unless it changes the user's next action

## README Style Rules
- Start with what the repo does
- Then the main entry points
- Then model / backend rules
- Then install
- Then run commands
- Then minimal layout notes if still useful
- How-to sections should be mostly bullets and code blocks
- Keep prose thin
- Prefer command-first examples
- Prefer one canonical example over many variations

## Comment Style Rules
- Comments must earn their keep
- Use comments for intent, invariants, contracts, hidden assumptions, and failure semantics
- Do not comment obvious syntax
- Keep comments short
- Prefer noun phrases or short imperative fragments when enough
- Good:
- `# attack roots mimic victim folder structure`
- `# fail fast on backend mismatch`
- `# preserve source filename for identity recovery`
- Bad:
- `# This function loops through the files and processes them one by one`
- `# Set the variable to the path`

## Warning / Error Text Rules
- Warning text should be direct
- Error text should say what failed and why
- Recovery hint only if short and actionable
- Avoid apology language
- Avoid vague wording like `something went wrong`
- Prefer:
- `dataset directory not found`
- `CUDA was requested but is not available`
- `existing output metadata does not match request`

## Formatting Rules For Human Text
- Prefer flat bullets
- No nested bullet trees unless structure is truly necessary
- Keep headings short
- Prefer concrete nouns over abstractions
- Prefer stable terms already used in the repo
- Avoid synonym drift across README, comments, metadata docs, and CLI help

## Reproducibility Rule For Writing
- New human-facing text should match this style unless a file already has a stronger local convention
- When rewriting existing docs, compress before expanding
- If a section can be expressed as bullets, do that
- If a warning can be shortened without losing meaning, shorten it

## Top-Level Entry Points
- `main_recognition.py`: current recognition / verification pipeline
- `main_attack.py`: attack-verification pipeline
- `modifier.py`: dataset materialization wrapper entry point

## Slowed Entry Points
- `slowed/main_recognition_slowed.py`: throttled recognition / verification pipeline
- `slowed/main_attack_slowed.py`: throttled attack-verification pipeline

## Recognition Pipeline
- Keep current structure and behavior as much as possible
- Input: one dataset root
- Flow: pairs -> embeddings -> verification metrics -> compiled results -> parsed tables
- Reuse cached outputs when present
- Model-specific scripts should generate embeddings only
- Recognition evaluation should use one shared route via `Recognition/evaluate.py`

## Attack Pipeline
- Input: clean gallery root plus attack method configuration
- Flow:
- clean gallery embeddings
- attack pair generation
- attacked probe materialization via `modifier.py`
- attacked probe embeddings
- attack verification metrics
- compiled results -> parsed tables
- Every step should skip if its output already exists
- Skip targets include embeddings, attack-pair files, generated attack datasets, metadata, metrics

## Layout
- `modifier.py`: wrapper CLI that dispatches to attack or non-attack materialization
- `Modifiers/preprocessing/`: corruption / degradation builders
- `Modifiers/protection/`: privacy / anti-recognition image-level methods
- `Modifiers/attack/`: face-swap / reenactment method wrappers
- `Utility/paths.py`: dataset naming / base-root / chain resolution
- `Utility/runtime.py`: shared paths, subprocess helpers, and model registry
- `Utility/slowed.py`: slowed-process orchestration helpers
- `Utility/results_compile.py`: compiled / parsed result rebuild helpers
- `Utility/results_parse.py`: readable result-table generation from `compiled_results.csv`
- `Recognition/materialize.py`: non-adversarial dataset materialization workflow
- `Recognition/metadata.py`: non-adversarial transform metadata contract and matching logic
- `Recognition/pairs.py`: clean pair generation helpers
- `Recognition/evaluate.py`: shared clean / corruption / protection verification evaluator
- `Attack/materialize.py`: adversarial dataset materialization workflow
- `Attack/metadata.py`: adversarial metadata contract and matching logic
- `Attack/pairs.py`: hard / semi-hard attack pair generation from embeddings
- `Attack/evaluate.py`: shared impersonation / attack-success evaluator
- `Models/<Model>/generate.py`: dataset root -> embeddings

## Dataset
- Root form: `Dataset/<dataset>/<transform_chain>_<base_root>`
- Clean roots are canonical references such as `main`, `train`, `val`
- Recognition variants preserve identity folders, filenames, and relative paths
- Preprocessing and protection variants change pixels only
- Attack variants use the same folder form: `folder/id_xxxxx/img_xxxxx`
- Attack variants contain false / manipulated faces, not clean originals

## Naming
- Base root is always the rightmost suffix token
- Transform chain sits left of the base root and uses `__`
- Chain order is newest-leftmost
- Adding a new modifier or attack prepends a new token
- Samples:
- `jpeg_q30__blur_sigma2_main`
- `faceswap_simswap_main`
- `reenactment_fomm__jpeg_q30_main`

## Attack Dataset Rule
- False-face attack roots should mimic the current dataset structure exactly
- Folder name = claimed identity / victim identity
- Output file name must retain the original source file name exactly
- Original identity should not be inferred from the folder in attack roots
- Original identity should be recovered from preserved filename plus dataset lookup / `identity_CelebA.txt` at the most efficient point in the pipeline
- Filesystem semantics are the primary source of truth for attack datasets
- Metadata JSON should only record information that is not safely inferable from structure and naming
- Full per-sample manifests are not required by default

## Attack Metadata
- Every attack root must include a compact JSON metadata file defined by `Attack/metadata.py` and written by `Attack/materialize.py`
- The JSON is a small derivation record, not a method catalog or full semantic restatement of every sample
- Required dataset-level fields:
- `input_dataset_dir`
- `output_dataset_dir`
- `base_dataset`
- `referenced_base_root`
- `variant_name`
- `attack_method`
- `generator`
- `seed`
- `pair_input`
- `num_requested_pairs`
- `num_written`
- `num_failed`
- `folder_identity_rule`
- `filename_rule`
- `attacker_resolution_rule`
- `path_semantics_are_primary`
- Optional fields:
- generator parameters not already encoded in the variant token
- notes about non-standard assumptions
- failure records for samples that could not be generated
- Per-sample records should be omitted unless they are necessary to explain failed or ambiguous cases

## Reproducibility Rule
- Attack generators must be deterministic given method config, source-target pair, and seed
- Attack generators must write all effective parameters to metadata
- Attack generators must not silently rename files
- Attack generators must not silently drop samples without logging
- If a sample fails, it must be recorded explicitly in metadata
- Skip philosophy: if output + metadata already exist, compare metadata against the current execution request
- If metadata matches, skip reuse is allowed
- If metadata mismatches, stop and raise instead of silently reusing or overwriting
- Do not add a separate reproducibility utility just for this check; perform the comparison inside the relevant materialization path

## Attack Pairing
- `Attack/pairs.py` input: embeddings file or model result directory
- Output: `<variant>_<model>_atkpairs.npz` and `.json`
- Pairing basis: identity centroid cosine similarity, then image cosine similarity
- Prefer similar non-matching identities to maximize realistic impersonation pressure
- Pair count / strictness is controlled by `top_k`, `samples_per_identity_pair`, `min_identity_sim`, `min_image_sim`
- Support at least:
- `hard`: nearest non-match identities
- `semi_hard`: sample from a high-similarity candidate pool

## Attack Shortlist
- Priority shortlist should cover the main attack families relevant to face verification:
- Face swap:
- `simswap`: practical high-fidelity face-swap baseline
- `faceshifter`: stronger occlusion-aware face-swap baseline
- Reenactment:
- `fomm`: canonical lightweight reenactment baseline
- `liveportrait`: stronger recent portrait-animation / reenactment baseline
- Adversarial impersonation:
- `advfacegan`: recent dual-identity impersonation model; especially relevant for source-preservation-aware evaluation
- Morphing:
- `mipgan`: representative GAN-based morphing baseline
- `mordiff`: representative diffusion-based morphing baseline
- Keep method names simple and stable at the CLI / path level
- Avoid a heavy per-method spec layer unless the pipeline genuinely needs it
- Methods may still rely on external backends or generator scripts

## Gallery / Probe
- Recognition mode may still use one dataset root symmetrically
- Attack mode should treat gallery and probe separately
- Gallery should usually be clean enrolled identities
- Probe should usually be manipulated attack images
- Future-friendly CLI shape should separate gallery and probe concepts clearly, even if the immediate CLI remains simple

## Pairs
- Pair source is derived from the referenced base root only
- Pair path: `Dataset/pairs/<dataset_relative_base_root>_pairs.npz`
- All variants ending in the same base suffix reuse the same pair file
- Shared clean pairs remain valid for recognition mode
- Attack mode must rely on attack pair files plus compact attack metadata, not only clean pairs

## Modifier
- `python3 modifier.py <dataset_dir> --step <modifier_spec> [--step ...] [--pair-input <atkpairs>]` -> derived variant root
- Output root stays under the same dataset parent
- `modifier.py` is a wrapper entry point only
- Non-adversarial steps dispatch to `Recognition/materialize.py`
- Adversarial / pair-driven steps dispatch to `Attack/materialize.py`
- Optional `--pair-input` restricts work to referenced images or pairs, depending on mode
- If derived root already exists, warn and skip unless `--force`
- Reject exact duplicate transform tokens already present in the input chain
- Reject duplicate transform tokens repeated within the same run
- `Recognition/metadata.py` defines the `transform.json` structure and request-matching rules
- `Attack/metadata.py` defines the compact attack metadata JSON structure and request-matching rules
- Non-adversarial variants keep `transform.json` as the metadata file
- Adversarial variants keep a compact attack metadata JSON instead of a full per-sample manifest

## Models
- `Models/<Model>/generate.py`: `<dataset_dir> <embeddings_out>` -> embeddings
- Models remain embedding backbones
- Models do not define attack success by themselves
- Models must not generate their own pairs
- Models should not own their own verification logic when they emit standard embeddings

## Evaluators
- `Recognition/evaluate.py`: `<pairs_file> <embeddings_file> <metrics_out>` -> verification metrics for all embedding backbones
- `Attack/evaluate.py`: `<gallery_embeddings> <probe_embeddings> <attack_metadata_json> <metrics_out>` -> attack metrics for all embedding backbones
- Attack evaluation must report requested samples, scored samples, failed samples, and skipped samples
- Attack metrics should include:
- `attack_success_rate`
- `victim_accept_rate`
- `attacker_accept_rate`
- `asr_at_far`
- `delta_vs_clean`
- `mean_clean_impostor_similarity`
- `mean_clean_margin`
- `mean_attack_delta_vs_clean`
- `mean_margin_closure`
- `mean_residual_margin`
- `mean_source_preservation_score`
- `source_preservation_accept_rate`
- `constrained_attack_success_rate`
- clean-margin-binned attack summaries

## Design Rules
- recognition / attack orchestration is split into `main_recognition.py` and `main_attack.py`
- domain pipeline code should live under `Recognition/` and `Attack/`
- reusable helpers should live under `Utility/`
- slowed orchestration is split into `slowed/main_recognition_slowed.py` and `slowed/main_attack_slowed.py`
- each domain may keep its own metadata module when that is clearer than forcing a shared abstraction
- change reminder: refactor `Recognition/materialize.py` to feel closer to `Attack/materialize.py`
- target for that refactor: keep `Recognition/materialize.py` as one workflow file, keep metadata contract / request-matching in `Recognition/metadata.py`, and continue reducing helper sprawl so the file reads as a more linear materialization flow
- utility cleanup reminder: keep `Utility/` as true shared infrastructure only; in particular, clean up `Utility/results_compile.py` by fixing stale package references, reusing `Utility/runtime.py` helpers where it stays cleaner, and only leaning on `Utility/paths.py` when that reduces inference noise rather than forcing abstraction
- Attack evaluation must become a first-class pipeline, not a small add-on to recognition evaluation
- Attack studies should report attack-specific thresholded and difficulty-aware metrics, not only balanced pairwise verification accuracy
- Filesystem semantics should be primary for attack datasets; metadata should supplement only what cannot be safely inferred
- Prefer lean method tokens and path-driven semantics over duplicated spec metadata

## Keep
- Existing embedding generators
- Dataset-root naming system
- Shared clean pair system
- Preprocessing and protection modifiers
- `transform.json`
- Shared evaluator routes
- compiled results + parsed readable outputs

## Remove or De-emphasize
- Treating every dataset root as symmetric verification-only data
- Using only balanced genuine/impostor accuracy as the main headline result
- Encoding attack semantics only through folder names

## Invariants
- Same referenced base root always maps to the same clean pair file
- Results are isolated by variant and model
- Attack roots must be reproducible through path semantics + compact attack metadata
- No silent sample loss, silent renaming, or silent parameter drift
- No training, fine-tuning, relabeling, or uncontrolled augmentation in the core benchmark unless explicitly added as a separate research branch
